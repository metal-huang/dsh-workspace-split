# DESIGN 多会话并置技术方案

创建日期：2026-10-22

## 本文件回答的问题

在 [PRD 多会话并置](../prd/20261022_PRD_多会话并置.md) 定下需求之后，
本文件回答「具体怎么做」：数据模型怎么建、槽位怎么接、状态怎么存、
里程碑怎么拆。

可复用的 DSH 能力清单见
[TECH DSH 现有能力盘点](../tech/TECH_DSH现有能力盘点.md)，本文件不重复。

## 一、总体结构

插件分四层，每层职责单一：

```text
┌─ 展示层 ─────────────────────────────────────────┐
│  SplitRoot     挂在 main 槽位，分屏模式的总入口   │
│  CellFrame     一个格子的外壳：头部 + 内容 + 边框 │
│  CellHeader    标题、状态灯、角标、切换条、操作   │
└──────────────────────────────────────────────────┘
┌─ 状态层 ─────────────────────────────────────────┐
│  LayoutStore   窗口、格子、当前格、比例的单一真源 │
│  CellRegistry  格子到会话持有引用的映射           │
│  StatusFeed    状态灯数据，轮询或订阅两种取数方式 │
└──────────────────────────────────────────────────┘
┌─ 接线层 ─────────────────────────────────────────┐
│  slotBridge    注册到 DSH 槽位的部分              │
│  sessionBridge 持有会话、取状态的部分             │
│  persist       布局持久化                        │
└──────────────────────────────────────────────────┘
┌─ 配置层 ─────────────────────────────────────────┐
│  上限设置、状态灯刷新方式                        │
└──────────────────────────────────────────────────┘
```

展示层不直接调 DSH 服务，一律经过状态层。这样槽位契约变动时，
改动范围被限制在接线层。

## 二、数据模型

### 2.1 窗口与格子

```ts
// 一个可独立分屏的窗口，一个显示器对应一个
interface SplitWindow {
  id: string;              // 窗口自身的标识，稳定不变
  cells: Cell[];           // 格子有序列表，顺序即渲染顺序
  activeCellId: string;    // 当前格
  geometry: Geometry;      // 该窗口内部的切分方式
}

// 一个格子
interface Cell {
  id: string;              // 格子标识，稳定不变
  windowId: string;        // 所属窗口
  sessionId: string | null;// 装的会话，空表示未装填
  scope: CellScope;        // 会话切换条的候选范围
  collapsedComposer: boolean; // 输入框是否折叠
}

// 会话切换条的候选范围
interface CellScope {
  kind: 'global' | 'workspace'; // 全局最近活跃，或限定在某项目下
  workspaceId?: string;         // kind 为 workspace 时必填
}

// 窗口内部的切分方式
type Geometry =
  | { kind: 'preset'; preset: PresetId; ratios: number[] }
  | { kind: 'custom'; splits: Split[] };

type PresetId = 'two' | 'three' | 'four' | 'six' | 'mainPlusStack';

// 一条分割线，可选吸附到屏幕交界
interface Split {
  id: string;
  direction: 'row' | 'column'; // 横向切或纵向切
  ratio: number;                // 两侧占比，0 到 1
  snapToScreenEdge: boolean;    // 是否吸附到显示器交界
}
```

`snapToScreenEdge` 为真时，该分割线的位置不由 `ratio` 决定，
而是读取显示器布局后对齐到交界处。这是单窗口跨屏方案的关键字段：
用户在界面里点一下「对齐到屏幕交界」，插件算出交界位置并把线挪过去，
其余分割线保持相对比例不变。

### 2.2 设计取舍说明

**格子顺序即渲染顺序**：布局用一个有序数组表达，重排即改数组顺序。
不引入树形结构，因为嵌套分屏对「并行监督」没有额外价值，
而数组让序列化、持久化、交换操作都变成一行。

**几何与内容分离**：`Cell` 只管装什么会话，`Geometry` 只管怎么切。
拖分割条改 `Geometry`，拖会话进格子改 `Cell`。
两者互不干扰，这让「分屏状态不变」在代码层面有了结构保证——
改变当前格只改 `activeCellId`，天然碰不到 `Geometry`。

**格子标识稳定不变**：格子标识由创建时生成并持久化。
这样布局持久化后，重启仍能对上号。

### 2.3 上限的判定

按 PRD Q1c 的收敛规则，实际可开格数取两层中更严格的那个：

```ts
function allowedCells(requested: number, all: SplitWindow[]): number {
  const total = all.reduce((n, w) => n + w.cells.length, 0);
  const globalRemaining = globalLimit - total;
  const capped = Math.min(requested, singleWindowLimit);
  return Math.max(0, Math.min(capped, globalRemaining));
}
```

2026-10-23 修订后，`singleWindowLimit` 默认 10，`confirmOverCells` 默认 6：
请求超过 6 格时界面先弹确认框；超过 10 格时界面拒绝生效，并提示用户
到插件配置里调大 `maxCells` 解锁。软限制不参与 `allowedCells` 的裁剪，
只控制确认框的出现。

三个数值来自配置层，手填值优先于按内存等指标自动推导的值，
留空则回到自动推导。

## 三、槽位接线

| 用途 | 接入点 | 说明 |
|---|---|---|
| 分屏模式总入口 | `main` 槽位 | 按注册键选择，注册分屏视图。注册键必须持久化，原因见 3.3 |
| 左上角进入按钮 | `shell.leading` | 窗口框架左上角的座位 |
| 格子里的会话体 | `conversation.content` 可实例化模板 | 每格一个实例，绑定各自会话 |
| 每格输入框 | 模板自带的 `conversation.composer.bar` | 不自己画，折叠状态由外层控制 |
| 设置项 | `settings.general.item` | 上限、状态灯刷新方式 |
| 未读提示 | `shell.overlay` | 跨格子汇总的提示条，可选 |

### 3.1 每格如何拿到会话体

`conversation.content` 是可实例化模板，一个格子实例化一次，
并绑定该格子的会话。实例化后的会话体内部包含输入框等子槽位，
这些子槽位的作用域是「会话」，因此每个实例的输入框天然独立。

### 3.3 主面板注册键必须持久化

主面板标识不是一组固定取值，而是一个品牌类型，
唯一构造途径是往 `main` 槽位注册时给出的注册键。
谁注册谁就产出一个合法标识，运行时按注册表校验。

由此带来两个必须处理的点：

1. **注册键要随布局一起持久化。** 重启后若用新生成的键去切换主面板，
   会因未注册而报错。因此注册键生成一次后存入持久化数据，之后复用。
2. **分屏视图要能容忍被重置。** 当某个主面板消失时，
   布局层会把当前主面板标识清成空，界面退回默认会话视图。
   分屏视图需要处理这种情况：自身被卸载时收起分屏，而不是崩溃或卡住。

### 3.4 输入框折叠怎么实现

折叠是外层容器的显示控制，不是改输入框本身。
非当前格的 `collapsedComposer` 为真时，外层把输入框区域压成一行；
点击就地展开。展开只覆盖格子底部，不撑大格子、不重排。

这样做的前提是输入框归格子实例自己所有，外层只控制可见性与高度。

## 四、状态灯与未读角标

### 4.1 两种取数方式

按 PRD Q5，做成设置项，默认轮询。

| 方式 | 实现 | 说明 |
|---|---|---|
| 轮询 | 定时读取会话状态快照 | 默认，几秒延迟 |
| 订阅 | 订阅会话状态的可订阅快照 | 状态变化立刻亮灯 |

两者数据源相同，差别只在取数方式，因此切换无需重启、不影响布局。
`StatusFeed` 对上层暴露同一套接口，取数方式的差异在内部消化。

### 4.2 未读角标

角标的判据是「格子里的会话有新输出，且该格不是当前格，或者窗口未聚焦」。
实现方式：记录每个格子已看到的最后一条消息位置，与会话当前位置比较。

未读状态在以下时机清除：该格成为当前格、窗口获得焦点、用户点开角标。

## 五、持久化

### 5.1 双轨存储

| 数据 | 走哪条 | 理由 |
|---|---|---|
| 布局（窗口、格子、比例） | 本插件 Host 半侧的存储域服务，客户端经 `host.call` 转调 | 结构性、高频、需跨重启，按窗口与格子建表 |
| 用户偏好（上限、刷新方式） | 设置服务的命名空间（插件自有配置结构）+ 常规设置项槽位 | 客户端经远程接口直接读写，由设置服务投影成表单 |

存储域提供建域、读全部、写记录、删记录、写全局、关闭这几项能力。

> 注：存储域**只对插件的 Host 半侧开放**（bundle 原文：
> "It is available only to host code"），客户端半侧没有任何存储服务。
> 布局读写的往返路径是：客户端半侧经 `host.call` 到本插件的 Host 半侧，
> 再由 Host 半侧操作存储域。
> 用户偏好走设置服务，客户端经远程接口可直接读写
> （`update` / `replace` / `mutate`，带 `expectedRevision` 并发保护）。
> 以 JSON 落盘的实现只是存储的一个后端，不是插件接口。

布局需要跨重启保留。持久化内容：

```ts
interface PersistedLayout {
  version: number;          // 结构版本号，用于升级时迁移
  windows: SplitWindow[];   // 全部窗口及其格子
  activeWindowId: string;   // 最后交互的窗口
  settings: {
    singleWindowSoftLimit: number | null;  // 空表示自动推导
    singleWindowHardLimit: number;
    globalLimit: number | null;            // 空表示不限制
    statusFeedMode: 'poll' | 'subscribe';
  };
}
```

写入时机分两类：

- 结构性变化（增删格子、改比例、换会话、切当前格）：变化后立即写入，
  并做一次防抖，避免拖分割条时高频写
- 非结构性变化（状态灯、角标）：不写入，这些是运行时状态

`version` 字段用于在结构升级时做迁移，老版本布局读到时先升级再使用，
读不懂则回退到默认布局。

## 六、与「分屏状态不变」对应的代码约束

PRD 原则二在代码上的落点，实现时逐条对照：

| 原则要求 | 代码约束 |
|---|---|
| 点击不改布局 | 点击只修改 `activeCellId`，任何代码路径都不得改 `Geometry` |
| 会话结束不重排 | 会话结束只更新状态灯，不触发格子增删 |
| 切换工作区不重排 | 布局按窗口存储，不含工作区维度 |
| 重启保持 | 走持久化，启动即恢复 |
| 唯一视觉变化是当前格边框 | 当前格的样式只改边框颜色，不改尺寸位置 |

建议在代码里把这组约束写成一条断言：任何修改 `Geometry` 的调用，
都必须来自显式的用户布局操作入口（拖分割条、换预设、增删格子）。

## 七、里程碑

按「先跑通单窗口全链路，再扩多窗口」的顺序。

| 阶段 | 目标 | 产出 |
|---|---|---|
| M1 | 单窗口四宫格，会话可装填、可切换、持久化 | 可用最小版本 |
| M2 | 每格可输入，输入框折叠展开，当前格标记 | 原则一落地 |
| M3 | 状态灯与未读角标，两种取数方式可配置 | 并行监督价值成立 |
| M4 | 单窗口跨屏：识别屏幕布局、分割线吸附到屏幕交界、跨屏预设 | Q1b 落地 |
| M5 | 上限配置与动态推导 | Q1c 落地 |

M1 到 M3 是核心价值，M4 与 M5 在其后。

### 7.1 M4 的前置风险：原生窗口能力已核实为不可用

**核查结论：DSH 插件体系不提供创建或控制原生桌面窗口的接口。**

证据三层：

- 客户端侧全部服务（八个）里没有窗口相关方法，布局服务只有切换主面板、
  开关右栏、开关侧边栏这几种能力
- 服务端全部服务清单中，`window` 一词只出现在会话事件读取的返回类型里，
  那是「读取会话事件的一段区间」的意思，与界面窗口无关
- 客户端全部事件里没有窗口相关事件

因此「一个显示器一个原生窗口」这条无法通过插件直接实现。
**这影响 PRD 的 Q1b，需要一个替代方案。**

### 7.2 M4 首选方案：单窗口跨屏铺满

**多显示器场景的首选做法是一个窗口铺满多个屏幕，而不是开多个窗口。**

界面本体是网页，一个网页窗口可以被拉伸到覆盖多个显示器。
分屏格子铺满这个窗口后，把其中一条分割线对齐到两个屏幕的交界处，
就得到「左屏四格、右屏六格」的效果。

相对开多个窗口的优势：

- 不需要第二个窗口，用户不用手动去开
- 状态天然共享，不存在跨窗口同步问题
- 不需要用本地存储区分窗口身份
- 「当前会话全局只有一个」这条自动成立

需要插件做的三件事：

1. **识别屏幕布局**：读取各显示器的位置与尺寸，算出交界处在哪
2. **提供对齐到屏幕交界的分割线**：用户可一键把某条分割线吸附到屏幕边界，
   这是本方案里插件真正要做的活
3. **提供跨屏预设**：例如「双屏各四格」「左六右四」，
   预设直接按屏幕交界分好组

**能力边界，如实记录：**

- 窗口跨屏拉伸是操作系统的能力，界面本身只需铺满窗口，
  这部分不需要 DSH 额外开放接口
- 在桌面应用自带窗口里，窗口需要用户手动拉到跨屏，
  插件无法代劳窗口位置
- 在浏览器里访问界面时，插件可做得更多：可以用窗口管理接口
  读取多屏信息，甚至按算出的整屏范围直接开一个铺满的窗口
- 全屏状态下一个窗口通常只铺满一个屏幕，
  想要跨屏需要退出单屏全屏改为手动拉伸，这一点照实告知用户

### 7.3 备选方案：以浏览器窗口承载第二组分屏

当单窗口跨屏无法满足时才用这一条。例如用户希望两个屏幕各自独立全屏、
各自保留独立的窗口状态。

已确认的可用事实：DSH 的界面本体通过 HTTP 提供，服务端有取界面地址
与注册路由的能力。

```text
DSH 后端（单一，共享会话与运行状态）
   ↑ HTTP                ↑ HTTP
第一个界面窗口         第二个界面窗口
（本机应用窗口）       （浏览器新开一个窗口，指向同一地址）
  布局 A                布局 B
```

**窗口标识用浏览器窗口各自的本地存储区分，各窗口据此读写各自的布局。**
这是唯一用本地存储的地方，与第五节所说的持久化是两条不同的路：
本地存储只用来告诉每个浏览器窗口「你是第几个窗口」，布局数据本身
仍由后端统一持久化。

这一条契合 PRD 的 Q4「分屏跟窗口」——窗口标识就是布局归属的单位。

代价：第二个窗口需要用户手动打开一次，且两个窗口之间无法共享当前格状态。

### 7.4 方案降级顺序

按以下顺序选择，每降一级同步更新 PRD：

1. 单窗口跨屏铺满（7.2，首选）
2. 浏览器第二窗口（7.3，用于需要各自独立全屏的场景）
3. 单窗口内浮层：用全屏浮层承载第二组分屏，可快速切换，
   局限是不能同时看见两组
4. 只做单窗口分屏，多显示器场景由用户自行用操作系统窗口管理处理

降级只影响 M4，M1 到 M3 的核心价值不受影响。

## 八、待确认项

1. **软限制推导公式**：需要真机实测多个输入框常驻的开销后才能定。
2. **主面板注册键的运行时全集**：静态查不到，取决于运行时有哪些插件
   注册了主面板槽位。实现时按运行时注册表读取，不写死取值。

## 九、已解决项

1. **原生窗口能力**：已核实为不可用，结论与方案见 7.1 与 7.2。
2. **主题与配色**：已确认可用主题令牌十三项，含背景、边框、品牌色、
   状态色（出错、空闲、成功、警告）。分格边框与状态灯直接取用这些令牌，
   不自定义颜色，因此自动跟随明暗主题。
3. **持久化接口**：双轨，见第五节。布局走本插件 Host 半侧的存储域服务
   （客户端经 `host.call` 转调），用户偏好走设置服务的命名空间。
4. **会话列表数据源**：拖拽源用 `ctx.sessions.list` 快照——它是会话元数据的
   权威来源（bundle 原话），零远程调用。检索方法仅在需要全文搜索时用。
   按项目限定候选范围时，结合工作区服务的会话归属关系。
   `sidebar.workspaces` 槽位是整块界面的替换点，不提供会话数据，不作为数据源。
